Femi9 · Program Guide

The Thara Model

Femi9's opt-in customer referral and loyalty program. A tiered personal discount, ten percent of a friend's order as store credit, and one percent that compounds every quarter into an Amazon voucher — layered on top of the storefront a customer already knows.

01What the model is

Any registered Femi9 customer can enroll, complete a qualifying purchase, and then earn three stacked benefits — going forward, on their own orders and on the orders of anyone they refer.

i.

Personal discount

On the member's own orders, tiered by cart value.

10 – 20Percent, by slab
ii.

Referral commission

Ten percent of a friend's paid order lands as Femi9 store credit.

10Percent · store credit
iii.

Quarterly voucher

One percent of a friend's paid order becomes points; every quarter they multiply by three into an Amazon voucher.

1 × 3Percent × Multiplier

Referred customers do not need to enroll to buy — they're regular shoppers to Femi9. Enrollment is only what unlocks earning power for the referrer.

Single-level referral tree. Person A refers B and C. A earns on B's and C's purchases. If B later refers D, only B earns on D — A does not. No cascade, no multi-level structure.

03Enrollment lifecycle

A member moves through four possible states. Activation happens automatically — inside the same database transaction that captures the qualifying payment — so a member can never end up "active" without a paid order behind them.

NON-MEMBER │ │ POST /api/thara/enroll { termsVersion } │ — auto-issues a unique 8-char referral code ▼ purchase_pending ◄─────────────────────────┐ │ │ admin unsuspends │ pays for order with subtotal ≥ ₹3,000│ → status is restored to │ (activation happens INSIDE the │ whatever it was before │ markOrderPaid DB transaction) │ the suspension ▼ │ ACTIVE ─────── admin suspends ────────► SUSPENDED │ │ POST /api/thara/opt-out ▼ DEACTIVATED (terminal for this user account — code is preserved as an audit anchor but treated as invalid on /r/[code])

Activation is server-authoritative. The promotion purchase_pending → active runs inside the same DB transaction as markOrderPaid, and stamps the qualifyingOrderId at the same moment. This guarantees the two facts — you have paid, you are active — cannot drift apart.

Every Thara member gets a unique referral code: four uppercase letters, then four digits. Ambiguous characters are omitted on both sides so a code shared in WhatsApp is unambiguously transcribable.

What happens when someone clicks a referral link

Friend receives https://femi9.in/r/TARA5578 (WhatsApp, SMS, in person) │ │ GET /r/TARA5578 ▼ ┌─────────────────────────────────────────────────┐ │ /r/[code] route │ │ │ │ 1. Feature flag off? → 404 │ │ 2. Code malformed? → 302 / │ │ 3. Code not found? → 302 / │ │ 4. Referrer suspended/off? → 302 / │ │ 5. Otherwise: set signed HttpOnly cookie │ │ femi9_thara_ref = jwt(referrer.id) │ │ TTL 30 days, aud=femi9-thara-ref │ │ → 302 to / │ └─────────────────────────────────────────────────┘ │ ▼ Friend browses, adds to cart, eventually signs up.

The cookie is signed with AUTH_SECRET (HS256, distinct audience femi9-thara-ref) so a hostile shopper cannot hand-craft one crediting an arbitrary member.

What happens when the friend signs up

All three sign-in paths — phone OTP, email magic link, Google — flow through the same helper attributeReferralIfPresent. It runs immediately after the User is created or matched, and is fire-and-forget: attribution failure never blocks sign-in.

Guards, in order:

  1. No femi9_thara_ref cookie → skip.
  2. Cookie signature invalid → skip.
  3. Referrer id doesn't resolve to a membership → skip.
  4. Referrer is suspended or deactivated → skip.
  5. The friend and the referrer are the same user → reject (self-referral).
  6. The friend's verified email matches the referrer's → reject (duplicate account).
  7. The friend's phone matches the referrer's → reject (duplicate account).
  8. The friend already has a TharaReferral row (unique constraint) → reject (one referrer per user, forever).
  9. Otherwise: create the row, stamp ipAtSignup + uaAtSignup.
  10. Clear the cookie either way.

When the referral becomes permanent

Attribution is created at signup with lockedAt = null. Admin can delete an obviously-fraudulent row during this window. The referral becomes permanent on the friend's first paid ≥ ₹3,000 order — inside the same transaction as activation, so state stays coherent.

05Personal discount  Shipped · sub-project B

Applied to the Thara member's own orders. Slab-based on cart subtotal, before shipping.

Order subtotalDiscount
Below ₹3,000—
₹3,000  to  ₹5,99910%
₹6,000  to  ₹8,99915%
₹9,000 and above20%

Rules

  • Member must be active. A purchase_pending member sees no discount on their first order — that first ≥ ₹3,000 order pays full price and activates them for future orders.
  • Discount is computed on subtotal (before shipping).
  • No stacking with promo coupons. The system picks the better of the two at checkout, not both.
  • Applied server-side at order creation. The client preview is not authoritative — what the server writes to Order.discount is.
  • Below ₹3,000: normal order at full price. No partial slab, no discount.
Worked example
Cart subtotal ₹4,000
Applicable slab ₹3,000–₹5,999 · 10% off
Discount ₹400
Payable ₹3,600 (before shipping)

06Referral commission  Shipped · sub-project C

Every time a downline user pays for an order, the referring Thara member earns 10% of that order's subtotal as Femi9 store credit, credited to their account and auto-applied at their next checkout.

Downline user pays ₹3,000 order │ │ (inside markOrderPaid transaction) ▼ Look up TharaReferral where referredUserId = downline.id │ │ If lockedAt is set (permanent referral): │ earn = 10% × subtotal = ₹300 ▼ Append to TharaCreditLedger: { userId: referrer.userId, delta: +30000 paise, reason: 'referral-commission', sourceOrderId: downline_order.id } Balance = SUM(delta) over all rows for that user.

Rules

  • Requires the referrer to be active. A purchase_pending member's downline purchases produce no commission until they complete their own qualifying order. Past downline purchases do not backfill.
  • Requires the referrer to be not-suspended. Suspended members earn nothing during the suspension window.
  • Applies to any downline order — no minimum. A ₹500 order earns ₹50 credit.
  • Applied automatically at the referrer's next checkout. No coupon code, no opt-in — the credit reduces the payable amount and debits the ledger in the same transaction.
  • Store credit only. Not withdrawable to bank / UPI. Not transferable. Persists as long as the account exists — no expiry.

Ledger design

Append-only. Every credit is a positive delta. Every debit (spent on a future order) is a negative delta linked to the order that consumed it. Every refund reversal (see §8) is a negative delta linked back to the original commission row. Balance is always SUM(delta). Historical rows are never mutated.

07Reward points & quarterly voucher  Shipped · sub-project D

Every downline order also generates 1% of subtotal as reward points, distinct from the store credit. Points accumulate over a rolling three-month cycle. At the end of the cycle, points × 3 is issued as an Amazon voucher.

Downline user pays ₹3,000 order │ │ (inside markOrderPaid transaction) ▼ earn = 1% × subtotal = ₹30 = 30 points │ ▼ Append to TharaRewardPointsLedger: { userId: referrer.userId, delta: +30, reason: 'referral-points', sourceOrderId: downline_order.id, cycleId: current_open_cycle.id } At end of cycle (cron on the 1st of the quarter): total_points = SUM(delta) for the closed cycle voucher_value = total_points × 3 (₹) Create TharaVoucher { userId, cycleId, points: total_points, valueRupees: voucher_value, status: 'available', claimDeadline: cycleClose + 30 days } Amazon Incentives API → issue real gift-code → attach. Fallback: admin pastes codes via /admin/thara/vouchers.

Cycle timing

  • Fixed calendar quarters (Q1: Jan–Mar, Q2: Apr–Jun, Q3: Jul–Sep, Q4: Oct–Dec) — admin-configurable if a different rhythm is preferred later.
  • Voucher is issued within the first hour of the next quarter.
  • Voucher must be claimed within 30 days of issuance or it expires.
Worked example · full cycle math
Referrer A active
Person B buys ₹3,000 · A earns ₹300 credit + 30 points
Person C buys ₹8,000 · A earns ₹800 credit + 80 points

Credit this cycle ₹1,100 — usable at next checkout
Points accrued 110
At cycle close 110 × 3 = ₹330 Amazon voucher

Rules

  • Same eligibility as commission — active and not suspended.
  • Points are not spendable directly; they only become a voucher at cycle close.
  • No expiry mid-cycle. Points become vulnerable to expiry only once they turn into a voucher.
  • Unclaimed vouchers expire after 30 days.

08Refunds & reversals

If a downline order that generated commission and/or points is later refunded, cancelled, or otherwise reversed, the earnings tied to that order are reversed too.

  • Any refund state — cancelled, refunded, partially_refunded — triggers reversal.
  • Full reversal on full refund. A ₹3,000 order that generated ₹300 credit + 30 points is fully reversed: ₹300 debited, 30 points debited.
  • Proportional reversal on partial refund. A ₹5,000 order refunded to ₹2,000 leaves ₹3,000 kept. Commission is recomputed on the kept amount: 10% of ₹3,000 = ₹300 → the ₹200 difference from the original ₹500 is debited; points scale proportionally.
  • Ledger stays append-only. Reversal writes a negative-delta row referencing the original earning row. The original row is never edited.
  • Negative balance is allowed. If the referrer has already spent the credit at another checkout by the time the refund happens, their balance goes negative. They cannot spend more until fresh earnings restore it to ≥ 0.
  • Voucher-stage reversal. If points were already rolled into an issued voucher and the voucher has not been claimed, the voucher value is reduced. If already claimed and used, no clawback of the Amazon code — the ledger records a negative delta as a soft claim against future earnings.

14Common questions

What if a member enrolls but never buys anything?

They stay in purchase_pending forever. Their referral link still works and can capture attributions, but when a referred friend pays, only the friend's activation and lock happen — the referrer earns nothing because they themselves are not yet active. If the referrer later completes their own qualifying order, they become active and future downline orders start earning. Past ones do not backfill.

Can two members share a phone number?

No. User.phone has a database-level unique constraint. There's exactly one User per phone number in the system, so this edge case is impossible.

What if the referrer opts out after a friend has been attributed but before that friend's first paid order?

The referral row exists but lockedAt is null. Because the referrer's membership is now deactivated, no commission or points would accrue on the friend's future purchases either way. The row stays as an audit record.

Does the personal discount apply to the qualifying (first ≥ ₹3,000) order?

No. Activation happens inside the same transaction that marks the order paid, but discount computation runs earlier (at checkout, when the order is created). So the first qualifying order pays full price and unlocks the discount for future orders.

Can a member share their referral link publicly?

Yes. There's no per-code rate limit on /r/[code]. But fraud detection watches for high-volume attributions from the same IP/UA cluster — if it looks like link-farming, admin can suspend.

What happens to a suspended member's earnings?

Already-accrued store credit stays in their ledger. Already-issued vouchers stay valid until their claim deadline. New commission and points do not accrue during the suspension window.

Can a customer be both a Thara member and a downline user of someone else?

Yes. Enrollment and being-referred are independent facts. The customer earns on their downline's orders (Benefits 2 & 3), and their own referrer earns on the customer's orders (from that referrer's perspective, the customer is a downline user).
